# MULTIMIND DESIGN DNA — MIGRATION BATCH MAP v1
## Human-readable deployment grouping for the locked 271/271 EQ3 corpus

**Status:** PROPOSED MIGRATION ORGANIZATION — does not change canonical DNA identity or the locked 271 denominator.

This document reorganizes the calibrated Design DNA corpus into migration-friendly batches. It is intentionally easier to read than the calibration ledger.

> Migration batch membership is operational packaging, not ontology.
> A DNA keeps its canonical ID, lineage, owner, resolver contract, provenance, and EQ3 contract regardless of which migration batch carries it.

---

# 0. Recommended migration hierarchy

I recommend **not** migrating in the old calibration Batch 1–9 order.

Use four layers:

1. **Foundation / Engines** — resolver, Material, Environment, shared primitives.
2. **Reference Theme Families** — Cultural tiers, Country-Web, Personal Media, Music.
3. **Composition / Torture Fixtures** — benchmark marriages.
4. **Asset enrichment** — after structural/asset-off projection works.

This lets us prove the machinery first, then progressively increase identity complexity.

# 18. WHY THIS IS BETTER THAN MIGRATING THE OLD CALIBRATION BATCHES VERBATIM

Calibration batches answered:

> “Have all 271 units reached the same EQ3 standard?”

Migration batches need to answer:

> “In what dependency order can we safely turn those contracts into a real running system?”

Those are different problems.

Therefore:

**CALIBRATION BATCH ≠ MIGRATION BATCH**

The migration order should follow runtime dependency and risk, not research history.

`SELECT BATCH → IMPLEMENT → TEST → GOVERNOR REVIEW → PATCH FAILED UNITS → ACCEPT → LOCK → NEXT`
